## 3. 計測方法と区間の定義
- 動作軽減を **比較対象（基準）** として使用。モーション有効 vs 動作軽減（emulate）を各 3 回。実行ごとにブラウザを新規起動、条件は交互（motion1, reduce1, motion2, ...）。
- 各実行: ログイン → ウォームアップ（A, C を 2 回, B の往復を各 1 回、計測外）→ ホームで静止 → 計測。
- 計測値は Flutter profile ビルドの `performance` measure（`Frame` 等）と PerformanceObserver(longtask) から取得。**FPS は直接は取得できない**ため、スクロール区間の「Frame 数 ÷ 時間」を参考値として示す（表示更新数であり実描画FPSではない）。
- A: 開始 = ホームの「出席管理」カードの pointerup。窓 = 開始から 3 秒。
- C: 開始 = 日付ピッカー「決定」の pointerup（ピッカー表示までは計測外、15日→14日）。窓 = 3 秒。
- B: 顧客一覧（60 名）で、同じ位置 (195,500) に wheel deltaY=150 を 30 回、66ms 間隔（約 2 秒、距離 4500px）。窓 = 最初の wheel ～ 最後の wheel + 1 秒。
- 終了の定義: 「最後の重いフレーム(>16.7ms)の終了時刻」を主指標とした。意図した演出の時間（遷移 250ms＋入場）は含まれるため総時間では比較しない。
- トレース: 別実行（run 9、`bench.js ... 1`）で CDP tracing（devtools.timeline 等）を A/B/C 各操作について保存（`traces/*.json.gz`）。トレース自体が負荷になるため、中央値の表（run 1〜3）には使っていない。
- 録画: 別実行（run 8、`REC=1`）で A/B/C のスクリーンキャスト（`recordings/*.mp4`）。

## 5. トレース・録画から読み取れたこと
- A（遷移）: 動作軽減でも通常でも、遷移直後に **長いフレーム（Layout 80〜215ms）が 2〜3 回**ある（run 1〜3 の最大 145〜261ms）。両条件で出るため演出が原因ではなく、出席画面の初回レイアウト（またはデータ到着後の再レイアウト）が原因の可能性が高いが、**原因箇所は特定していない**。この環境（ソフトウェア描画・仮想 4 vCPU）での値。
- A（通常のみ）: 遷移後 1.5 秒以降も Flutter フレームが出続ける（73/80/83 回、約 49回/秒、1 フレーム約 4ms）。在室中ドットの無限パルス（3 名）によるもので設計どおり。動作軽減では 0 回。カクつきではないが、**常時 CPU を使う要素**ではある。
- C（日付切替）: 両条件ほぼ同じ（長いフレーム 1 回 約 65〜70ms、約 200〜250ms で収束）。録画上も引っ掛かりなし。
- B（スクロール）: 両条件で同等。Frame 処理時間の中央 約 6ms、p95 約 17〜19ms。16.7ms超は 5/7/13 と 4/17/7 で **ばらつきが大きく**、条件間の差とは言えない。33ms超は 0〜2 回、長いタスク（>50ms）は各条件で 1 回以下。録画でも停止は見えない。
- トレース（run 9）: GPU プロセスの GPUTask は 16ms 超なし。メインスレッドの 50ms 超タスクは A で 3〜4 回、C で 1 回、B で 0〜1 回。

## 6. 言えること／言えないこと
言えること: この環境（headless Chrome 141・SwiftShader ソフトウェア描画・390×844・上記データ）では、
C と B に継続的なカクつき・操作不能は見られず、A に遷移直後の一時的な長いフレーム（最大 約 180〜260ms、両条件）がある。
動作軽減の初期反映と起動後の双方向切替は、押下縮小・カード入場・スケルトンのパルスで動きの変化を確認した。
言えないこと: 現場 PC / iPad / 実 GPU での快適さ、体感の保証、IME・実テンキー・スクリーンリーダー・地図、起動時間（対象外）、
A の長いフレームの根本原因。
**この結果をもって「性能問題なし」とは結論しない。**
