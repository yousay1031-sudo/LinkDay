# 本番への反映手順（ステップ1：データ共有化／Firestore 移行）

この手順書は、作業用ブランチ `feature/firestore-shared-data` の内容を本番（プロジェクト `linkday-proud`）に反映するためのもの。
**作成時点（2026-11-19）では、何も本番に反映していない**（deploy・push・main への反映は未実施）。実施は承認を得たうえで、人が行う。

## 0. 前提と注意

- **反映する順番を守る**：ルール → 事業所と所属の登録 → アプリの公開。
  - 新しいアプリは、ログイン後に `memberships/{uid}` を読み、`facilities/{facilityId}/…` を読み書きする。ルールと所属が先に無いと、全画面が「データを読み込めませんでした」または「事業所に登録されていません」になる。
  - 新しいルールは既存のコレクション（line_linkage, linking_codes, notification_logs, slots など）の扱いを変えていない。そのため、**ルールだけを先に反映しても、今の（Hive 版の）アプリはそのまま動く**（業務データは今のアプリでは Firestore に置いていない）。
- **既存のブラウザ内データは移さない**（試用段階のため入れ直す。指示書どおり）。
  - 今の Hive（各端末の IndexedDB）にある顧客・出席・週間計画・設定・送迎計画は、新しいアプリからは見えない。
  - 必要なら、公開前に今のアプリの顧客一覧を Excel で書き出しておき、公開後に「Excel一括インポート」で入れ直す。
  - 通知履歴（端末ごと）は Hive のまま残る。
- **検証ビルド（`build/verify_web`）を deploy しない**。公開するのは通常ビルド（`build/web`）だけ。
- Cloud Functions・インデックス・LINE の設定は、このステップでは変えていない。
  - 問い合わせは単一フィールドの条件だけなので、複合インデックスは不要。`firestore.indexes.json` は変更なし。
  - Functions は deploy し直さない。
- Maps の API キーは、今までどおり各端末の設定画面で入れる（Firestore には置かない）。新しいアプリでも、端末ごとに入れ直しは不要（SharedPreferences は同じ）。

## 1. 公開版のビルド環境を Flutter 3.50 に切り替える（条件E）

開発と検証は Flutter 3.50 で行い、`pubspec.lock` もそれに合わせて更新した（コミット「環境更新：Flutter 3.50 に合わせた…」）。
公開版も同じ版でビルドする。

1. 公開用のビルドを作る環境（端末または CI）の Flutter を 3.50 にする。
   - `flutter --version` で 3.50 系であることを確かめる。
2. リポジトリの `main`（反映後）を取得し、`flutter pub get` を実行する。`pubspec.lock` が書き換わらないことを確かめる（`git status` が空）。
3. `flutter analyze`（info 56 件以内）と `flutter test`（全件通過）を実行する。
4. `flutter build web --release` を実行する（`--dart-define=LINKDAY_VERIFY=true` は付けない）。出力は `build/web`。
   - 通常ビルドに検証用のコードが入っていないことは、`main.dart.js` が検証用の変更の有無で同一であることで確認済み（検証構成の修正時）。

## 2. 公開前に全画面の見た目と動きを見直す（条件E）

検証環境（`docs/VERIFY_ENV.md`）で、**公開する版と同じコミット**の検証ビルドを使い、人の目で全画面を確かめる。自動の確認（puppeteer）では見ていない点を中心にする。

| 画面 | 見直す点 |
|---|---|
| ログイン → 事業所の確認 | 読み込み中の表示、「事業所に登録されていません」画面、通信不可の画面と再試行 |
| 画面上部の担当者の帯 | 全画面で帯が出る・重ならない・押せる。担当者の選択画面。日付が変わったときの表示 |
| ホーム | 件数（受給者証期限・出席未処理・超過見込み）が他の端末の変更で更新される |
| 顧客管理 | 一覧・検索・絞り込み・編集・新規登録・在籍終了（確認文言）・「在籍終了の顧客」と在籍に戻す・Excel 取込・送迎場所の位置確認 |
| 週間利用計画 | 翌週から開くこと（変えていない）・マスの操作・時刻の変更・再生成・翌週へのコピー・PDF・スマホ幅の曜日タブ |
| 出席管理 | 入室・退室・欠席・欠席の取り消し・処理中の表示・通信不可時の「再試行」・競合時の案内・LINE 応募の表示・時刻の修正・PDF |
| 送迎計画 | 表示・除外・並び替え・自動グループ分け・最適化・地図（Maps の API キーがある端末で）・PDF |
| 設定 | 事業所・座標・車両・運営時間・受付時間・管理者 userId・API キー・職員（担当者）の追加と在籍終了・アプリ情報 |

- 2台（または通常ウィンドウとシークレットウィンドウ）で、片方の変更が開き直さずにもう片方に届くことを、主な画面で確かめる。
- スマホ幅（390px 前後）とタブレット幅でも見る。
- Maps の API キーを使う確認（座標取得・最適化・地図）は、検証環境では動かない。本番反映後に、限られた端末で確かめる（手順 6）。

## 3. Firestore のルールを反映する

1. `firestore.rules` が作業用ブランチの最終版であることを確かめる。
2. ルールテストを実行する：`tool/verify/test_rules.sh`（最初に、エミュレータが今のルールで判定していることを確かめる。33 件すべて通過すること）。
3. 本番に反映する（**ルールだけ**）：
   ```bash
   firebase deploy --only firestore:rules --project linkday-proud
   ```
4. Firebase コンソールの「ルール」で、反映されたルールの日時と内容を確かめる。必要ならルールのシミュレーターで次を試す。
   - 未認証で `facilities/{事業所ID}/customers/x` の読み取り → 拒否
   - 所属のないアカウントで同じ読み取り → 拒否

## 4. 事業所と所属を登録する（クライアントからは書けないため、管理者がコンソールで行う）

1. Firebase コンソール → Authentication で、事業所のログイン用アカウントの **UID** を確かめる（共用端末で使うアカウント。複数あればすべて）。
2. Firestore → データ で、次の 2 種類のドキュメントを作る。
   - `facilities/{事業所ID}`：例 `facilities/kokostudy`、フィールド `name`（文字列、事業所名）。
     - 事業所ID は英数字とハイフン程度の短い ID にする。後から変えられない（業務データはすべてこの下に入る）。
   - `memberships/{UID}`：フィールド `facilityId`（文字列、上の事業所ID）、`createdAt`（タイムスタンプ）。アカウントごとに 1 件。
3. 職員（担当者）は、アプリの設定画面から登録する（最初の 1 人は「初期設定」として記録される）。コンソールでの作成は不要。
4. 事業所の設定（事業所名・住所・車両など）は、アプリの設定画面から入れる。保存するまでは既定値で動く。

## 5. アプリを公開する

1. 手順 1 で作った `build/web`（通常ビルド）を公開する（**Hosting だけ**）：
   ```bash
   firebase deploy --only hosting --project linkday-proud
   ```
2. 各端末で、ページを再読み込みして新しい版になったことを確かめる（Service Worker のため、1 回目は古い版が出ることがある。もう一度再読み込みする）。

## 6. 公開後の確認

1. ログイン → 所属の確認 → ホーム画面に進むこと。
2. 設定画面で職員を登録し（初期設定）、画面上部の帯で担当者を選ぶ。
3. 顧客を 1 名登録（または Excel 取込）し、別の端末で開き直さずに見えること。
4. 週間利用計画・出席・送迎計画・設定で、1 件ずつ記録して、別の端末で見えること、記録に担当者が残ること（Firestore コンソールで `updatedByStaffName` を確かめる）。
5. Maps の API キーがある端末で、事業所の座標取得・送迎ルートの最適化・地図が動くこと（検証環境では未確認の項目）。
6. LINE の空き枠通知は従来どおり（欠席の保存後に候補画面が出る）。実際の送信は職員が確認してから。

## 7. 問題があったときの戻し方

- アプリだけ戻す：Firebase コンソール → Hosting → リリース履歴から、1 つ前のリリースに戻す。
  - 今の（Hive 版の）アプリに戻れば、各端末の Hive にある元のデータがそのまま見える（新しいアプリは Hive の業務データを消していない）。
  - 新しいアプリで Firestore に記録した内容は、古いアプリからは見えない。
- ルールは戻さなくてよい（古いアプリは業務データを Firestore に置いていないため影響しない）。戻す場合は `git show bc3ca0c:firestore.rules` の内容を反映する。

## 8. 反映後に残る既知の事項（範囲外として報告済み）

- 通知履歴（空き枠 LINE 通知の送信記録）は端末ごと（Hive）のまま。
- 定員の固定値 10 は設定の「1日の最大利用者数」を使っていない。
- 出席の記録が無い状態で入室すると、名前が空の記録ができることがある。
- LINE 連携用のコレクションは、ログインしていればどの事業所のアカウントでも読める（今は 1 事業所なので影響なし。複数事業所にする前に見直す）。
- 送迎の停留所を除外・並び替えしても、距離・時間は再計算されない。
- 1 週間に自動で作れる週間計画のマスは 499 件まで。
- 設定画面の「アプリ情報」のフレームワークの版の表示（Flutter 3.35.4）は古いまま。
