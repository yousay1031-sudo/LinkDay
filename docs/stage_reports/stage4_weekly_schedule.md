# 段階4（週間利用計画）の報告

作業用ブランチ `feature/firestore-shared-data`。main（`bc3ca0c`）には触れておらず、push もしていない。deploy はしていない。

## 変更したファイル

**保存先の切り替え（「1週間＝1データ」から「顧客×日」へ分割）**
- `lib/services/weekly_schedule_service.dart`：Hive をやめ、Firestore の次の2つに保存する。
  - `scheduleEntries/{YYYY-MM-DD}_{顧客ID}`：利用予定1件（顧客×日）
  - `scheduleWeeks/{weekKey}`：「この週は作成済み」を示す目印
- **公開メソッドは名前も引数もそのまま**にした。`getOrCreateSchedule`、`saveSchedule`、`addEntry`、`removeEntry`、`updateEntryStatus`、`updateEntryTimes`、`regenerateFromRegularDays`、`copyScheduleToNextWeek`、`getEntriesForDate`、`countUsageByCustomer` など。
- 画面には、これまでどおり `WeeklySchedule`（週 → 7日 → 予定）の形で渡す。
- **購読**：週ごとに購読する。他の端末の変更は、画面が持っている同じオブジェクトの中身を書き換えて反映し、変更を通知する（`ChangeNotifier`）。
  - ログイン後は「今月の初め〜4週先」を先に読み込む。
  - それ以外の週は、開いたときに読み込む（`ensureWeek` / `ensureRange`）。
- **書き込み**：前回の内容と違うマスだけを、1回の一括書き込み（batch）で送る。
  - この端末の書き込みが確定する前は、そのマスを古い通知で上書きしない。
- **担当者**：記録を変える操作には担当者が必要。
  - 担当者を先に確かめてから画面の内容を変える。選択を閉じたら何も変えない。
- **週の自動作成**：画面を開いた週がまだ無ければ作る。
  - トランザクションで「目印がまだ無い」ことをサーバーで確かめてから書く。2台が同時に開いても1回だけ作られる。
  - 担当者は不要で、「自動」と記録する。
  - 全員の予定を消した週は、目印が残るので、定期利用曜日から作り直さない。
- `lib/data/data_session.dart`：ログイン後に購読を始め、ログアウトで止める。
- `lib/main.dart`：週間利用計画の Hive ボックスを開く処理を削除。
- `lib/services/attendance_service.dart`：`ensureTodayScheduledRecords` は、その日の週を読み込んでから判定する。
  - 読み込む前に判定すると「計画なし」として、誤って定期利用曜日から作ってしまうため（設計どおり）。出席の保存先そのものは段階5で移す。
- `lib/services/monthly_usage_service.dart`：集計の前に、対象月の週を読み込む。
- `lib/screens/transport_screen.dart`：選んだ日の週を読み込んでから利用予定者を出す。

- 確かめた内容：
  - 1マス＝1ドキュメント（`{日付}_{顧客ID}`）と、週の目印で保存される。自動作成は「自動」と記録される。
  - **同じ週の別のマスを2台で編集しても、両方の変更が残る**。画面が持っている同じオブジェクトに、もう一方の変更が反映される。

  - 担当者が未選択なら編集を止め、画面にも保存先にも反映しない。

  - 定期利用曜日からの再生成では、追加とキャンセルを残し、予定だけを作り直す。

## 判断が必要な点・気づいた点

1. **通信が切れた状態で、まだ無い週を開いたとき**：トランザクションが使えないため、「週間利用計画を作成できませんでした（通信できません…）」と知らせる。そのうえで、定期利用曜日から作った案を、保存しないまま表示する。
   - そのまま編集すると、その週の全マスと目印が保存される。
   - その間に他の端末がその週を作っていた場合は、後勝ちになる。
   - 承認済みの設計にはこの場面の扱いが書かれていなかったので、この扱いでよいか確認したい（代わりに「通信が戻るまでその週は表示しない」こともできる）。
2. **週を一度に作れるマスは499件まで**（Firestore の1回の書き込みの上限は500件）。
   - 今の60名では、1週あたり約170件。
   - 1日あたり約80名を超える事業所では、自動作成を分割する必要がある。今は対応していない。
3. エミュレータのルールが古いまま残る問題（段階3の報告の1）は、今回は起きなかった。ルールテストを実行したあとも、検証用プロジェクトの読み取りが正常にできることを確かめた。
