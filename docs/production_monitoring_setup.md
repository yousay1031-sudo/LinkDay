# 本番運用・監視設定手順（人間がやる作業）

Day 12 の本番公開にあたり、コンソール上で行う監視・予算・障害対応の設定をまとめる。
**Maps API だけでなく、Firebase（Functions / Firestore / Hosting）と LINE を含めた全体**が対象。

対象プロジェクト: **linkday-proud**（Blaze プラン）
本番 URL: https://linkday-proud.web.app

> 既存の `docs/google_cloud_budget_alert.md` は Maps API に特化した詳細手順。
> 本書はそれを含む**全体の監視設計**として位置づける。
> Maps のクォータ上限など細部はそちらを参照すること。

## 1. 【最優先】Google Maps API キーに本番ドメインを追加

**この作業を行わないと、本番 URL で地図が真っ白になる。**
現在のリファラ制限には開発用ドメインしか入っておらず、
`linkday-proud.web.app` からの呼び出しは `RefererNotAllowedMapError` で拒否される。

### 手順

1. [Google Cloud コンソール](https://console.cloud.google.com/) を開く
2. プロジェクト選択で **linkday-proud** を選ぶ
   （Maps キーを別プロジェクトで発行している場合はそちらを選ぶ）
3. 左メニュー → **「APIとサービス」→「認証情報」**
4. LinkDay で使用している API キーをクリック
5. **「アプリケーションの制限」** が **「HTTP リファラー（ウェブサイト）」** であることを確認
6. **「ウェブサイトの制限」** に以下を**追加**する

```
https://linkday-proud.web.app/*
https://linkday-proud.firebaseapp.com/*
```

7. 既存の開発用エントリは**残してよい**（下記参照）
8. **「保存」** をクリック

### 開発用リファラの扱い

| リファラ | 扱い | 理由 |
|---------|------|------|
| `https://linkday-proud.web.app/*` | **本番・必須** | これが無いと本番で地図が動かない |
| `https://linkday-proud.firebaseapp.com/*` | **本番・必須** | Hosting の別名ドメイン |
| `http://localhost:*/*` | **残す** | 本番公開後もローカル開発を続けるため |
| `https://*.sandbox.novita.ai/*` | **残す（ただし期限を決める）** | 開発サンドボックス用 |

> **sandbox.novita.ai を残すことのリスク**:
> このドメインは開発環境の共有ドメインであり、LinkDay 専用ではない。
> 同じドメイン配下の別サンドボックスからキーを使われる可能性がゼロではない。
> **開発が完全に終わったら削除すること**。
> 当面残す判断であれば、後述のクォータ上限（1日あたり）を必ず併用する。

### 「API の制限」の確認

同じ画面の下部で、**「キーを制限」** が選ばれ、以下 3 つのみ許可されていることを確認する。

- Maps JavaScript API
- Geocoding API
- Routes API

「制限なし」になっている場合は、キーが流出したときに
翻訳 API や Vision API など全サービスを使われる。必ず制限する。

### 反映確認

設定保存後、**最大 5 分**で反映される。本番 URL で以下を確認する。

1. 送迎計画画面を開く → 地図が表示される
2. 顧客編集 → 送迎場所に住所を入力 → 候補が出る（Geocoding）
3. 送迎計画 → ルート最適化 → 経路が描画される（Routes API）

失敗する場合は、ブラウザの開発者ツール（F12）→ Console で
`RefererNotAllowedMapError` が出ていないか確認する。
出ていれば、リファラの綴り（`https://` の有無、末尾の `/*`）を見直す。

## 2. 全体予算アラート（Maps + Firebase を統合）

`docs/google_cloud_budget_alert.md` では Maps API に絞った予算を作成した。
Blaze プラン移行後は **Firebase の従量課金も同じ請求先アカウント**に乗るため、
**プロジェクト全体の予算**を 1 本作ることを推奨する。

### 手順

1. Google Cloud コンソール → **「お支払い」→「予算とアラート」**
2. **「予算を作成」**
3. 設定内容

| 項目 | 推奨値 |
|------|--------|
| 名前 | `LinkDay 全体予算` |
| 時間範囲 | 毎月 |
| プロジェクト | **linkday-proud**（サービスは絞らない） |
| 割引・クレジット | 「クレジットを割引として含める」をオン |
| 金額 | **月 1,000 円**（想定はほぼ 0 円のため、動いたら異常） |

4. しきい値（4 段階）

| しきい値 | 種別 | 意図 |
|---------|------|------|
| 50% | 実際の費用 | 月中の進捗確認 |
| 90% | 実際の費用 | 早期警告 |
| 100% | 実際の費用 | 予算到達 |
| 100% | 予測額 | 「このペースなら超える」事前警告 |

5. 通知先メールを運用担当者に設定 → **完了**

### 想定コスト（参考）

| サービス | 想定利用 | 無料枠 | 想定費用 |
|---------|---------|--------|---------|
| Cloud Functions | 1日数件の通知 + webhook | 200万呼び出し/月 | **0 円** |
| Firestore | 3コレクション・少量 | 5万読み取り/日 | **0 円** |
| Hosting | 静的配信（約 30 ファイル） | 10GB転送/月 | **0 円** |
| Maps JavaScript API | 操作時のみ地図表示 | 月 $200 クレジット | **0 円** |
| Geocoding / Routes | 座標は Hive にキャッシュ済み | 同上 | **0 円** |

**月 1,000 円のアラートが鳴ったら、それ自体が異常のサイン**として調査する。

## 3. Firebase 使用量の確認

Firebase コンソールには Cloud Billing のような「予算アラート」は無いため、
**定期的な目視確認**か、Cloud Monitoring のアラートで代替する。

### 3-1. 目視確認（月 1 回を推奨）

1. https://console.firebase.google.com/project/linkday-proud/usage
2. 以下を確認

| 指標 | 確認箇所 | 注意ライン |
|------|---------|-----------|
| Functions 呼び出し数 | Usage → Cloud Functions | 月 10万回を超えたら調査 |
| Firestore 読み取り | Usage → Firestore | 日 1万件を超えたら調査 |
| Firestore 書き込み | 同上 | 日 1,000 件を超えたら調査 |
| Hosting 転送量 | Usage → Hosting | 月 5GB を超えたら調査 |

LinkDay の想定規模では、いずれも桁違いに小さい値にとどまるはず。
急増している場合は、無限ループや外部からの不正アクセスを疑う。

### 3-2. Cloud Monitoring でアラート化（任意・推奨）

1. https://console.cloud.google.com/monitoring/alerting
2. **「ポリシーを作成」**
3. 指標: `Cloud Functions > Function > Execution count`
4. 条件: 1 時間の合計が **1,000 回を超えたら** 通知
5. 通知チャンネルにメールを登録 → 保存

これで、webhook が無限ループした場合などに早期に気づける。

## 4. 【重要】LINE 月200通無料枠の管理

### 既知の制限（未実装機能）

> **LinkDay には、当月の送信数カウントと残枠表示の機能がありません。**
> 通知送信画面には「あと何通送れるか」が表示されません。
> 無料枠を超えると**送信が失敗し、保護者に通知が届かなくなります**。
> 残数の把握は、下記の手動確認に頼っている状態です。
> （実装は将来タスク。`docs/release_notes_v1.md` の「今後の拡張候補」を参照）

### 残数の確認手順（**月 2 回以上を推奨**）

1. [LINE Official Account Manager](https://manager.line.biz/) にログイン
2. 対象アカウント（ココスタディ）を選択
3. 左メニュー → **「分析」→「メッセージ通数」**
   または ホーム画面上部の **「今月の無料メッセージ通数」** 表示
4. **当月の送信済み通数 / 200 通** を確認

### 通数の数え方（誤解しやすい点）

| 操作 | カウント |
|------|---------|
| 空き枠通知を 5 名に送信 | **5 通**（宛先ごとに 1 通） |
| 連携完了の自動返信 | **0 通**（応答メッセージは無料枠の対象外） |
| 友だち追加時のあいさつ | **0 通**（同上） |

**つまり、空き枠通知のプッシュ送信のみが 200 通を消費する。**
1 回の欠席で 5 名に送ると 5 通消費するため、
**月 40 回の欠席通知で上限に達する**計算になる。

### 上限が近いときの対応

| 残数 | 対応 |
|------|------|
| 残 50 通以下 | 送信対象を絞る（本当に来られそうな児童のみ） |
| 残 10 通以下 | 電話連絡に切り替える |
| 0 通 | 当月はプッシュ送信不可。翌月 1 日にリセット |

有料プラン（ライトプラン 月5,000円で5,000通）への移行も選択肢だが、
現在の利用規模では**まず無料枠で運用し、実績を見てから判断**するのが妥当。

## 5. 障害時の一次対応手順

### 5-1. 症状別の切り分け

| 症状 | 最初に見る場所 |
|------|--------------|
| 画面が真っ白 | ブラウザ F12 → Console のエラー |
| 地図だけ出ない | Console に `RefererNotAllowedMapError` → 本書 1 を実施 |
| ログインできない | Firebase コンソール → Authentication → Users |
| LINE 通知が届かない | Functions ログ（下記 5-2） |
| 「送信機能がサーバーに見つかりません」 | Functions が未デプロイ → 再デプロイ |
| 「アプリの読み込みが不完全」 | ブラウザのハードリロード（Ctrl+Shift+R） |

### 5-2. Cloud Functions のログを見る

```bash
cd /path/to/linkday_app

# 直近の通知送信ログ
firebase functions:log --only sendVacancyNotice --limit 20

# LINE webhook のログ（連携がうまくいかないとき）
firebase functions:log --only lineWebhook --limit 20

# 全関数のログ
firebase functions:log --limit 50
```

**ログの読み方（よく出るもの）**

| ログ内容 | 意味 | 対応 |
|---------|------|------|
| `push result ... "status":"sent"` | 送信成功 | 正常 |
| `invalid signature rejected` | 署名検証に失敗 | `LINE_CHANNEL_SECRET` が誤り。再設定して再デプロイ |
| `status 401` | トークンが無効 | チャネルアクセストークンを再発行して再設定 |
| `status 429` | **無料枠超過またはレート制限** | 本書 4 で残数を確認 |
| `status 400 ... invalid user` | 連携先の userId が無効 | 保護者がブロック/友だち解除した可能性 |

> ログには**トークンもシークレットも出力されない**設計になっている
> （`lineUserId` も末尾 4 桁のみのマスク表示）。
> ログのスクリーンショットを共有しても、秘密情報は漏れない。

### 5-3. Web コンソールでログを見る

CLI が使えない場合は、ブラウザからも確認できる。

https://console.cloud.google.com/functions/list?project=linkday-proud
→ 関数名をクリック → **「ログ」** タブ

### 5-4. 緊急時のロールバック

デプロイ後に不具合が出た場合、Hosting は直前のバージョンに戻せる。

1. https://console.firebase.google.com/project/linkday-proud/hosting/main
2. 「リリース履歴」から 1 つ前のバージョンの **︙** → **「ロールバック」**

Functions のロールバックは自動ではできないため、
直前のコミットをチェックアウトして再デプロイする。

```bash
git checkout <前のコミットハッシュ>
cd functions && npm run build && cd ..
firebase deploy --only functions
```
