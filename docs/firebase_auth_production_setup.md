Day 12 の本番公開にあたり、Firebase コンソールで行う認証まわりのセキュリティ設定をまとめる。
**アプリのコードからは設定できない項目**のみを対象とする。

対象プロジェクト: **linkday-proud**
本番 URL: https://linkday-proud.web.app

> 所要時間の目安: 15 分
> 作業前に、管理者アカウント（yamadaudemy555@gmail.com）で
> https://console.firebase.google.com/project/linkday-proud にログインしておく。

## 1. メール列挙保護（Email Enumeration Protection）の有効化

**目的**: 「このメールアドレスは登録されていません」という応答を返さないようにし、
どのアドレスが職員アカウントとして存在するかを外部から推測されないようにする。

1. Firebase コンソール → 左メニュー **Authentication**
2. 上部タブ **Settings（設定）**
3. **User actions（ユーザーアクション）** セクションを開く
4. **Email enumeration protection（メール列挙保護）** を **有効（Enable）** にする
5. **Save（保存）** をクリック

### 有効化後に起きる変化（職員への周知が必要）

- ログイン失敗時のメッセージが、原因を問わず
  「メールアドレスまたはパスワードが違います」に統一される。
- 「パスワードだけ間違えた」のか「そのアカウントが無い」のかを
  画面から区別できなくなる。**これは意図した仕様**。
- 職員から「ログインできない」と言われたら、
  コンソールの Authentication → Users でアカウントの存在を確認して案内する。

## 2. 未使用のサインインプロバイダを無効化

**目的**: 使っていない認証経路を塞ぐ。LinkDay は**メール/パスワードのみ**を使う。

1. Authentication → 上部タブ **Sign-in method（ログイン方法）**
2. 一覧を確認し、以下の状態にする

| プロバイダ | あるべき状態 |
|-----------|-------------|
| **メール/パスワード** | **有効** |
| メールリンク（パスワードなしでログイン） | 無効 |
| Google | 無効 |
| 匿名 | **無効**（重要） |
| 電話 | 無効 |
| Apple / Facebook / X / GitHub / Microsoft / Yahoo | 無効 |

3. 有効になっている不要なプロバイダをクリック → トグルを **無効** → **保存**

> **匿名認証は特に注意**。有効のままだと、Firestore ルールの `isSignedIn()` を
> 匿名ユーザーが通過してしまい、`line_linkage` / `linking_codes` を
> 誰でも読み書きできる状態になる。必ず無効を確認すること。

## 3. 承認済みドメイン（Authorized domains）の確認

**目的**: 認証を許可するドメインを本番と開発に限定する。

1. Authentication → **Settings** → **Authorized domains**
2. 以下が含まれていることを確認する（通常は自動登録済み）

| ドメイン | 用途 | 扱い |
|---------|------|------|
| `linkday-proud.web.app` | **本番** | 必須。消さない |
| `linkday-proud.firebaseapp.com` | 本番（別名） | 必須。消さない |
| `localhost` | ローカル開発 | 残してよい |

3. 開発用サンドボックス（`*.sandbox.novita.ai`）について
   - Firebase の承認済みドメインは**ワイルドカード不可**。
     サンドボックス URL はセッションごとに変わるため、恒久登録はできない。
   - 開発中にそのドメインでログインが必要になったら、
     その時点のホスト名を**一時的に追加**し、**開発が終わったら削除**する。
   - 本番運用だけを考えるなら、追加しないのが安全。

4. **身に覚えのないドメインがあれば削除する**（乗っ取りの足がかりになる）。

## 4. パスワードポリシーの設定

**目的**: 「password」「12345678」のような推測されやすいパスワードを拒否する。

1. Authentication → **Settings** → **Password policy**
2. **Enforce password policy（パスワードポリシーを適用）** を有効化
3. 推奨設定

| 項目 | 推奨値 | 補足 |
|------|--------|------|
| 最小文字数 | **10** | 既定の 6 は短い |
| 大文字を必須 | 任意 | 要件を増やすほど付箋に書かれやすくなる |
| 小文字を必須 | 任意 | 同上 |
| 数字を必須 | 推奨 | |
| 記号を必須 | 任意 | 現場の運用負荷と相談 |
| 適用モード | **Require（必須）** | Notify only は警告のみで弾かない |

4. **保存**

> 文字種の要件を増やすより、**長さを確保する**ほうが実務では有効。
> 現場で覚えきれない要件にすると、かえってメモ書きの放置を招く。

### 既存ユーザーへの影響

ポリシーを有効にしても、**既存のパスワードは即座に無効にならない**。
次回のパスワード変更時から適用される。
既存職員にも強いパスワードを使わせたい場合は、個別に再設定を依頼する。

## 5. 新規登録の停止（運用方針に応じて）

LinkDay は職員のみが使う業務アプリで、一般利用者の登録を想定していない。
アプリ内に登録画面がある場合でも、コンソール側で塞いでおくと安全。

1. Authentication → **Settings** → **User actions**
2. **Enable create (sign-up)** のチェックを**外す**
3. 保存

**この設定を行った場合の職員追加手順**:
Authentication → **Users** → **Add user** でメールアドレスと初期パスワードを登録し、
本人に初回ログイン後のパスワード変更を依頼する。

> 運用上、職員が自分で登録する前提にしているなら、この手順はスキップしてよい。
> その場合は「誰でも登録できる」状態である点を認識しておくこと。

本番 URL で、以下をひととおり確認する。

| # | 確認内容 | 期待結果 |
|---|---------|---------|

## 7. 補足: Web API キーについて

`lib/firebase_options.dart` に含まれる `apiKey` は、
**Web クライアントに配布される前提の公開値**であり、秘密情報ではない。
ブラウザの開発者ツールからも見える。

悪用防止は、キーを隠すことではなく以下の 2 点で担保している。

1. **Authentication の承認済みドメイン**（本手順の 3）
   → 許可ドメイン以外からの認証リクエストを拒否する
2. **Firestore セキュリティルール**（`firestore.rules`）
   → 未認証アクセスを全面拒否し、`notification_logs` はクライアント書き込み不可

したがって、このキーをリポジトリに含めること自体は問題ない。
**一方で、Google Maps の API キーは別管理**で、
リファラ制限を必ず設定すること（`docs/production_monitoring_setup.md` 参照）。
